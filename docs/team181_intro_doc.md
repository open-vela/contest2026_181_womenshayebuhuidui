## 摘要

本作品在**没有 WiFi 模组的穿戴级硬件**上，先解决「联网」这个前提问题，再把「主动」做成产品核心：
手表通过手机的蓝牙网络共享获得**一个真正的 IP 地址**（BNEP/PAN over BR/EDR + DHCP），
从而具备标准 socket 能力；在这个基础上，它按**时间**（闹钟叫醒）、按**阈值**（心率告警）、
按**空闲上下文**（主动关怀）三种方式主动开口，动作全部由设备端自主完成。

三个关键数字：

| 指标 | 结果 |
|------|------|
| 长稳回归 | **60.6 分钟 / 60 轮**：0 assert、0 断链、堆用量首尾持平 |
| 主动场景 | **3 个**，全部真机验证（含完整触发日志） |
| 平台贡献 | **3 项**公共仓缺陷修复，已提交 PR（是本作品联网能力的前提） |

> 起点说明：openvela 蓝牙框架中 PANU profile 从未被编入构建，zblue 也没有 BNEP 实现。
> 本作品补齐了 BNEP 编解码与 PAN SAL，并在此过程中定位并修复了三个平台移植层缺陷。

## 二、用户故事

产品叙事聚焦**留守儿童与独居老人**这类「身边长期没人」的人群。手表扮演的不是查询工具，
而是**会主动开口的陪伴者**。

| 场景 | 用户的问题 | 本作品的做法 |
|------|-----------|-------------|
| 早晨 · 起不来 | 没人叫，普通闹钟响一声就被按掉 | 到点前 1 分钟先预告 → 到点主动开口叫醒 → 2 分钟无反应升级催促；期间碰一下设备即视为「已读」并撤销催促 |
| 独处 · 没人说话 | 长时间静默，情绪无处安放 | 连续 5 分钟无互动主动开口（按时段选文案），并让语言模型顺着追问一句 |
| 身体 · 心跳异常 | 自己未必察觉，也没人提醒 | 心率超阈值主动告警；措辞只做「提醒」，不做「诊断」 |
| 日常 · 想设提醒 | 要掏出手机点半天 | 对手表说「35 分钟后提醒我吃药」，云端理解、设备自己执行 |

## 三、系统架构

### 3.1 联网：不走代理，走标准网络

常规做法是让手机 App 做一层私有协议代理，设备端只能访问被代理商定好的接口。
本作品让手表通过手机的**蓝牙网络共享**拿到真正的 IP 地址，于是设备端获得标准 socket 能力
——ping、DNS、HTTP、任何云端 API 都能直接用，**不需要手机侧配合做协议转发**。

```
┌────────────────┐  BNEP/PAN + DHCP  ┌────────────────┐  TCP / DNS  ┌──────────────┐
│ 智能体手表      │ ────────────────► │ 手机（被借用）  │ ──────────► │ 云端          │
│ SF32LB52       │                   │ 蓝牙网络共享    │             │ 标准 HTTPS    │
│ 无 WiFi 模组    │ ◄──────────────── │ 充当 NAP       │ ◄────────── │ 任意 API      │
└────────────────┘                   └────────────────┘             └──────────────┘
```

**实测**：冷启动无人干预即联网 → `dhcp_ok ip=192.168.44.140`；公网 IP 与域名 ping 均 0% 丢包。

### 3.2 端侧软件分层

```
应用层   桌宠页 / launcher / 历史对话窗口（LVGL 9.1）
         关怀调度器 pet_care：空闲关怀 · 闹钟状态机 · 心率告警
         心率模拟与阈值 health/hr_monitor
AI 层    agent 框架：消息总线 · LLM 路由（端云兜底）· 工具调用 · Skill 体系
         端侧语言模型（velaAI TFLM，兜底）· 云端 StepFun（主力）
系统层   openvela / NuttX · LVGL · 蓝牙协议栈（zblue + 自研 BNEP/PAN）
硬件层   SF32LB52（Cortex-M33）· FT6146 触摸 · LCD · 板载 MEMS 麦克风
```

**工程约束下的取舍**（SRAM 余量约 37 KB）：

- 关怀调度**零常驻线程**——`pet_care_tick` 挂在 LVGL render 线程上，用**墙钟秒**门控做 1 Hz 逻辑
- L2 文本生成复用既有 agent 线程，不新开线程

## 四、核心功能

### 4.1 主动能力 ×3（赛道核心区分点）

#### ① 定时主动：闹钟叫醒

- 状态机：`T-60s 预告` → `T0 叫醒`（含天气占位语）→ `T0+120s 无响应升级催促`
- 交互闭环：任何触摸/按键都视为「用户已醒」
- 真机日志（完整三段）：

```
[pet_care] fire emo=4  还有一分钟就到时间啦，准备好哦～
[pet_care] fire emo=5  叮～到点了！天气信息暂不可用，出门前记得确认天气
[pet_care] fire emo=6  嘿，还没动呢？我可要挠你痒痒了！
```

#### ② 阈值主动：心率告警

- 模拟心率随机游走（基线 65–95 bpm），超过阈值（默认 120）触发
- 单次事件只报一次 + 60 秒冷却，避免连环轰炸
- 真机日志：`fire emo=6 刚刚测到心跳有点快，先坐下歇会儿吧` + `hr alert 124 bpm`

#### ③ 上下文主动：空闲关怀

- 连续 5 分钟无互动 → 主动开口；22:00–07:00 静默不打扰；10 分钟冷却
- 触发后让语言模型顺着追问一句（L2 增强，失败静默，L1 模板已保底）
- 真机日志：冷启动后 **313 秒** → `fire emo=6 我在呢，想聊点什么吗？` + `Processing message from care:pet_care`

### 4.2 端云协同（赛道进阶要求）

云端 LLM 的工具集里没有设备闹钟——那是端侧模型的能力。本作品补齐了这一环：

| 层 | 职责 | 技术 |
|----|------|------|
| 云端 | 理解自然语言、决定调用哪个工具 | StepFun `step-3.7-flash`（标准 HTTPS + 工具调用） |
| 桥 | 把「要提醒」翻译为设备可执行动作 | 自定义 Skill `care-reminder` + 工具 `set_alarm` / `cancel_alarm` |
| 设备 | 预告、叫醒、催促、活动确认 | 关怀调度器（零常驻线程） |

**关键设计**：云端工具 `set_alarm` 与端侧工具 `set_timer` **指向同一个 `pet_care_alarm_set()`**，
因此「云端可用」与「云端不可用（自动兜底端侧模型）」两条路径行为完全一致，只有一份状态机。

真机实测（完整执行 trace）：

```
iter=0 tool=set_alarm                         ← 云端 LLM 主动调用设备工具
[pet_care] alarm set 40min                     ← 设备端闹钟设上
[tool_alarm] alarm armed for 40 min (cloud tool)
END status=ok iters=2 tools=1 backend=0        ← 全程云端，无兜底
[Agent]: 已设置 40 分钟后提醒您开会。
```

### 4.3 自定义 Skill：`care-reminder`（赛道基础要求）

Skill 是交给云端 LLM 的行为手册（Markdown，置于设备技能目录）。它解决一个具体缺口：

- 照默认行为，云端 LLM 处理「提醒我」会调用 `cron_add` 发一条**静默通知**——只出现在历史里，**叫不醒任何人**
- `care-reminder` 明确告诉它：来自手表的提醒请求**一律调用 `set_alarm`**

**一次真实的调参过程**（也体现 AI 协作方式）：

1. 首次演示：模型选择了 `cron_add`，且**没有读取 Skill 文件**——trace 中只有 `get_current_time` + `cron_add`，
   说明它仅依据**系统提示里的一行摘要与工具描述**做决策
2. 三个改动：技能摘要行写明「手表上的提醒一律用本技能（优先于 reminder/cron）」；
   `set_alarm` 工具描述补 `PREFER THIS over cron_add`；内置 `reminder` 技能内指向本技能
3. 立即可复现：`iter=0 tool=set_alarm` → 设备闹钟 armed → 自然语言确认

### 4.4 使用的 ai_agent 核心能力

| ai_agent 能力 | 本作品如何使用 |
|--------------|---------------|
| 消息总线（channel 机制） | 主动关怀的 L2 追问走 `care` 通道进入 agent loop；NSH `ask`、实体键提问复用同一管线 |
| LLM 路由器 + 端云兜底 | 云端优先，失败自动兜底端侧 TFLM 模型；两者共用同一执行路径 |
| 工具调用（Tool Calling） | 端侧 `set_timer`/`cancel_timer`；新增云端 `set_alarm`/`cancel_alarm` |
| Skill 体系 | 自定义 `care-reminder`，随固件内置 |
| LVGL UI 通道 | 气泡 + 情绪表情 + 历史对话窗口；跨线程访问统一串行化 |
| cron / 心跳基础设施 | 作为对照路径保留（静默通知），并在 Skill 中说明其与设备叫醒的区别 |

### 5.2 验收中定位并修复的两个真缺陷

**① LVGL 跨线程竞态（会导致界面永久僵死）**

- 现象：`ask` 之后 render 线程不再响应，屏幕与心跳模拟同时停摆
- 定位：`dumpstack` 显示其卡在 `usleep → nxsig_clockwait`——**线程没死，是「睡不醒」**
- 根因：本固件 LVGL 以 `LV_OS_NONE` 构建（无内部锁），agent 线程直接调用 `lv_async_call`
  与 render 线程的 `lv_timer_handler` 竞争同一条定时器链表，链表损坏后 render 自身的唤醒定时器一并失效
- 修法：新增加锁投递队列，所有跨线程 UI 调用由 render 线程统一落地；连续 3 次对话后 tick 均存活

**② 关怀调度实际频率只有设计的 1/5**

- 现象：关怀逻辑表现为「很慢」，曾被误判为线程停止
- 定位：实测 60 秒仅 12 次状态变化（≈0.2 Hz）；原实现按「每圈 5 ms × 200 圈 = 1 秒」计数，
  而 `lv_timer_handler` 使每圈实际约 25 ms
- 修法：改为**墙钟秒门控**，与循环速率解耦

### 5.3 如实记录的两次误判

工程日志中保留了两处判断错误的完整过程，供复现与复盘：

1. **「闹钟不响」**——实际是触发路径未写 syslog，串口里不可见；补齐日志后一次看清，闹钟一直是正常的
2. **「调度线程死了」**——实际是频率慢 5 倍，并非停止

> 过程与证据见 `docs_ble/LOG.md` Round 27。这类记录是「可维护性」的直接体现。
