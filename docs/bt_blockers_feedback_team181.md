# 关于 SF32LB52 蓝牙联网方案阻断点的技术反馈与支持请求

**致**：openvela AI 硬件开发者大赛组委会
**发自**：队伍 181（Sen70s）
**日期**：2026 年 8 月 13 日
**硬件**：SF32LB52-DevKit-LCD（思澈 SF32LB52-MOD-1，双模蓝牙 5.3，无 WiFi）

---

尊敬的组委会：

我队参赛作品基于 SF32LB52（无 WiFi 硬件）开发嵌入式 AI Agent。为实现真机联网以运行 LLM 对话，我队对全部可行的联网路径进行了逐条验证。现将各路径的阻断点与验证证据整理如下，恳请组委会协助对接相应资源。

## 一、背景与总体结论

设备无 WiFi，蓝牙为唯一无线通道。我队依次验证 5 条联网路径，结论如下：

| 编号 | 方案 | 阻断环节 | 结论 |
|---|---|---|---|
| 1 | 手机蓝牙网络共享（PAN/BNEP） | 框架层 | openvela PAN SAL 适配层缺失，无法加入手机网络 |
| 2 | 经典蓝牙 SPP（含官方 AI_AGENT_BLE_NET 代理路线） | 驱动层 | 30 余条 HCI 命令被 vendor 驱动本地模拟，从未下发至控制器 |
| 3 | BLE GATT NUS 数据通道（官方 App 路线） | 内存层 | 广播已由我队修复并空口验证通过；连接建立被预存内存越界写阻断 |
| 4 | USB RNDIS（非蓝牙备选） | 硬件层 | USB 控制器被调试串口独占，复合设备端点不足，硬件不可行 |

其中方案 3 为官方配套 App 的设计路线，当前仅差连接建立一环，是本次反馈的重点。

## 二、统一验证标准（监测点）

所有方案均按以下 5 个标准监测点验证，任一监测点未通过即判定链路不通：

| 监测点 | 验证内容 | 通过标准 |
|---|---|---|
| M1 命令链路 | HCI 命令是否真实下发、控制器是否响应 | 命令出现在驱动层发送日志，且 CMD_COMPLETE status=0x00 |
| M2 空口可见性 | 广播信号是否真实发射 | 手机 nRF Connect 与系统蓝牙双通道可见设备名与 UUID |
| M3 连接建立 | 对端连接请求是否被接受并上报 | 设备端出现连接完成事件（0x3E）与连接回调日志 |
| M4 数据流 | 连接后数据帧收发是否正常 | 双方帧往返完整、无错位 |
| M5 稳定性 | 长时间运行无崩溃 | 连接保持 5-10 分钟无 hardfault |

## 三、各方案验证情况与阻断点

### 3.1 手机蓝牙网络共享（PAN/BNEP）

**方案说明**：手机开启"蓝牙网络共享"，设备以 PANU 身份经 BNEP over L2CAP 接入手机网络。

**验证结果**：M1 未执行（无初始化代码可下发命令），M2-M5 不可达。

**阻断点**：openvela 框架具备 PAN API 头文件（`bt_pan.h`）与 profile 骨架（`panu_service.c`），但 SAL 适配层（`sal_pan_interface.h`、`bt_sal_pan_*` 系列接口）全工程无实现，`panu_service` 未参与编译。经核实，官方 dev 分支同样缺失。自行实现 BNEP over L2CAP 预计需 600-1000 行代码并涉及框架层改动。

**影响范围**：阻断所有基于系统级蓝牙共享的联网场景；不影响 BLE 链路。

**请求**：希望官方提供 PAN SAL 实现或 BNEP over L2CAP 的参考移植。

### 3.2 经典蓝牙 SPP

**方案说明**：经 BREDR SPP 通道承载 IP 数据（官方 `AI_AGENT_BLE_NET` 选项设计的"手机 App 蓝牙 SPP 代理上网"路线）。

**验证结果**：M1 未通过；M2-M5 不可达。

**阻断点**：vendor 驱动 `sf32lb52_bth4.c` 中的 `sf32lb52_bt_emulate_cmd()` 对 Write_Scan_Enable、Write_Local_Name、Write_Class_of_Device、Set_Event_Mask 等 30 余条 BREDR 命令进行本地模拟（直接合成 status=0 的 CMD_COMPLETE 返回上层），命令从未下发至 LCPU 控制器。驱动层发送日志中无上述命令。BREDR 链路的可发现性与连接参数从未被真实设置，端到端能力无法验证。

**影响范围**：阻断所有 BREDR 路线（SPP 直连、SPP 代理、PAN 底层链路）；不影响 BLE 链路。

**请求**：希望官方协助与思澈厂商确认 LCPU 固件对 BREDR 命令的支持情况，并澄清 bth4 模拟层的设计意图（哪些命令应真实下发）。

### 3.3 BLE GATT NUS 数据通道（重点）

**方案说明**：官方配套 App（com.agent.coapp）经 BLE GATT NUS（UUID 6e400001）与设备通信；设备端以 TUN + GATT 帧隧道承载网络数据，App 侧转发上网。

**验证结果**：

| 监测点 | 结果 | 说明 |
|---|---|---|
| M1 | 通过 | 9 条初始化命令全部真实下发且 CMD_COMPLETE status=0x00 |
| M2 | 通过（我队修复） | 详见下述修复说明 |
| M3 | 未通过（当前卡点） | 手机发起连接后 45 秒内设备端无任何连接事件 |
| M4、M5 | 不可达 | 连接未建立 |

**M2 修复说明（供官方参考）**：原扩展广播（0x2036/0x2037/0x2039）存在 LCPU 固件"假成功"现象（返回 status=0 但空口无信号）。我队参照官方 Gemini-S1 参考配置改为 legacy 广播（`CONFIG_BT_EXT_ADV_LEGACY_SUPPORT=y` 且广播类型为 `BT_LE_LEGACY_ADV_IND`）后，nRF Connect 实测广播类型为 Legacy，设备名 Agent-Watch 与 NUS UUID 6e400001 可见，信号强度 -43 dBm，空口验证通过。

**M3 阻断点证据链**：

1. zblue 协议栈计算 LE_SET_EVENT_MASK 命令掩码为 0x020f（bit0 为 LE 连接完成事件，取值正确）；
2. `sys_put_le64` 写入 net_buf 后立即读回，字节为 0f 02 00…（正确）；
3. 驱动层发送时字节变为 08 0f 02…（被改写，0x020f 变为 0x0f08）；
4. 错误的掩码下发至 LCPU 后，控制器屏蔽 LE Connection Complete（0x3E/0x01）事件；
5. 因此手机连接永远无法建立。

**阻断点结论**：zblue 的命令 net_buf 在写入正确值之后、发送之前被预存的内存越界写破坏。同源证据包括：文件系统 inode 链表节点被破坏（BFAR=0x00100121 精确总线错误）、关闭 GATT_CLIENT 配置后系统在语音/LVGL 初始化阶段确定性崩溃（恢复配置后消失）、崩溃点随机且受堆布局影响——均指向持续性越界写。

**影响范围**：该破坏源影响 zblue 全部 net_buf 数据通道（命令池与 ACL 收发池）。即使当前连接建立成功，后续数据流仍可能被同一破坏源污染（历史现象：连接建立后 bluetoothd 在 uv__io_poll 处 hardfault）。因此该问题阻断的是整个 BLE 数据面，而非仅连接环节。

**请求（最高优先级）**：希望官方协助定位 zblue 在 NuttX 平台上的内存破坏源（可能方向：net_buf 池管理、引用计数、与 LCPU IPC 的交互），或提供 SF32LB52 BLE peripheral 连接建立的可运行参考配置。

### 3.4 USB RNDIS（非蓝牙备选）

**方案说明**：设备 USB 虚拟网卡直连电脑，有线高速联网。

**验证结果**：USB 枚举未通过（电脑侧枚举超时 error -110/-71）；设备端 RNDIS 网络设备注册成功（eth1 出现）但 `usbdev_register` 返回 -EBUSY。

**阻断点**：

1. 芯片仅有一个 USB 控制器（封装内），当前被 CDC ACM 调试串口独占（烧录与调试依赖该串口），RNDIS 注册与串口互斥；
2. 板上两个 Type-C 接口并联同一控制器（实测互换接口串口不消失），并非独立通道；
3. 复合设备（串口与网卡共存）不可行：控制器仅 4 个端点（EP0 及 EP1-3），RNDIS 与 CDC ACM 各需 3 个端点，合计 6 个超出硬件能力；
4. 禁用串口换取 RNDIS 不可接受（烧录依赖串口，禁用后无法再次烧录）。

该路径为硬件约束，仅作记录。
